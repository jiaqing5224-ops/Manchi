## 1. D1 分析：解析应该是内置能力，不是独立组件类型

### 现状
- `sources.py` 的 `file` 源**已经**会把 `.xlsx/.xlsm` 用 openpyxl 转成文本（`_read_excel_as_text`）。
- 邮件源返回结构化邮件对象（正文/附件），文本源返回原文。
- 文档（docx/pdf）解析**目前不存在**（原方案已标注为绿地）。

### 推荐模型：解析 = 输入源责任 + 1 个通用解析组件
1. **输入源自动解析（内置）**：选择输入源后，系统按类型把原始数据预处理成"规整数据"再喂给第一个组件：
   - `mail` → 邮件对象列表（主题/发件人/正文/附件路径）
   - `file` → 按扩展名自动解析：`.xlsx/.xlsm/.csv` → 表格（行=dict 列表）；`.docx` → 文本；`.pdf` → 文本；`.txt` → 文本
   - 这样"选了邮件/Excel 默认就解析"，正是你要的内置行为。
2. **组件通过 `input_requirement` 声明期望的输入形状**（如 `excel`、`docx`、`mail`）。编排器在 UI 连线和运行时保证上游数据类型匹配，不匹配则告警。
3. **链路中途需要解析某个附件/文件时**：提供通用 `parse_file` transform 组件（按扩展名调用对应解析器），**不**为每种格式单开一个"解析XXX"组件。
4. **`standalone` / `source` 类组件无上游输入**，自然不要求输入源 —— 对应你说的"不选择输入源就是一个可直接运行的组件"。

### 好处
- 解析关注点集中、单一可测，不被复制进每个组件。
- AI 生成组件时只需写"处理逻辑"，不用重写解析。
- 组件契约保持简单：`transform(params, ctx) -> data`，`input_requirement` 仅为元数据约束。

## 2. D2 分析：组件类型与输入源约束（manifest 两层描述）

### 2.1 行为角色 `type`（4 类，沿用原方案并澄清）
| type | 含义 | 是否有上游输入 | 输出 |
|------|------|----------------|------|
| `source` | 自己从外部获取初始数据（邮件扫描/web抓取/读文件） | 否 | 初始 `current_data` |
| `transform` | 接收数据→转换→返回新数据（最常用，如 ai_extract） | 是 | 新 `current_data` |
| `output` | 产出文件/副作用，`current_data` 透传 | 是 | 透传原数据 |
| `standalone` | 无需输入、独立运行（如定时清理、纯计算） | 否 | 结果数据 |

### 2.2 输入形状约束 `input_requirement`（新增，回答"必须接邮件/excel"）
取值：`none` | `any` | `text` | `mail` | `excel` | `csv` | `docx` | `pdf` | `json` | `table` | `file`

- `input_requirement: none` → 只能作为链路起点（或 `standalone`/`source`）。
- `input_requirement: excel` → 编排器要求它前面必须是能产出表格的输入源/组件，否则 UI 标红 + 运行前告警。
- 解析后的数据形状由 D1 的源层保证，组件只声明"我需要什么形状"。

### 2.3 manifest 关键字段（在 `Manchi组件系统设计方案.md` 基础上补充）
```json
{
  "name": "excel_to_tasks",
  "display_name": "Excel工时转任务",
  "type": "transform",
  "input_requirement": "excel",
  "output_type": "any",
  "requires_input_source": true,
  "requires": ["openpyxl"],
  "params": { "...": {} }
}
```
> 原方案用 `input_type` 表达输入，本文建议改为更明确的 `input_requirement` + `requires_input_source` 布尔，避免与"输入源(source)"概念混淆。

## 3. D3 分析：组件开发边界（允许 / 禁止）

### 允许开发的组件类别
1. **数据转换类**：文本/字典/列表的处理、过滤、映射、聚合。
2. **文件 I/O 类**：仅在 `artifacts_dir` 或系统临时目录内读写。
3. **外部调用类**：HTTP API、数据库查询（需在描述中注明）。
4. **本地自动化类（你重点想要的）**：
   - 用 Python 标准库或已声明依赖做本地自动化（文件批量处理、重命名、压缩等）
   - 表格：`openpyxl`；文档：`python-docx` / `pdfplumber`；浏览器自动化：`playwright`/`selenium`（需写入 `requires`）
   - Windows COM：Outlook、Excel（`pywin32`）
5. **AI/LLM 类**：通过 `settings.json` 中配置的端点调用（不硬编码 key）。
6. **系统联动类**：在 Manchi DB 中创建任务记录等。

### 禁止（边界红线）
- 修改核心系统文件（后端代码、其他组件文件）。
- 持久化系统修改（注册表、系统服务、环境变量）。
- 在 `artifacts_dir` 外的破坏性文件操作（删除/覆盖用户文件）。
- 硬编码密钥/令牌 —— 一律通过 `params` 传入。
- 网络扫描、渗透测试、未授权访问。
- 执行来自不可信源的代码（组件本身即代码，导入他人组件视为信任授权）。
- 需要管理员提权/高权限的操作。

> 边界原则：**组件是"纯函数式的数据处理器 + 受限副作用"，所有可变配置走 params，所有产物走 artifacts_dir。**

## 4. D4 分析：依赖管理与导入合并机制

### 目录结构（与你的设想一致）
```
C:/Users/z0055h5c/Documents/Manchi/components/
├── registry.json            # 自动生成的元数据索引（可选）
├── requirements.txt         # 全局合并依赖清单（带注释标明来源组件）
├── install_deps.py          # 自动安装缺失依赖脚本
├── <name>.py                # 组件代码
└── <name>.manifest.json     # 组件元数据
```

### 导入合并流程（解决"别人导入用不了"）
1. 解压 `.zip` 到 `components/`（含 `<name>.py` + `<name>.manifest.json`）。
2. 读取 manifest 的 `requires`，**合并**进全局 `requirements.txt`（去重，注释标注来源组件名）。
3. 运行 `install_deps.py`：`pip install -r requirements.txt`，改为 **diff 模式** —— 用 `importlib.util.find_spec` 先检测已装，只装缺失项，避免重复安装。
4. 若安装失败（无网络 / 需本地编译的原生依赖）：
   - 标记组件状态为 `needs_setup`；
   - 在"组件管理"界面高亮提示"缺少依赖：xxx，请手动安装"；
   - 运行该组件前弹告警，不静默失败。

### 单组件可携带依赖（便于分享）
每个导出 `.zip` 内可附 `requirements.txt`（仅本组件依赖），导入时再 merge 进全局，兼顾"单组件独立分享"与"全局统一管理"。

### 版本策略
第一版**不锁版本号**（直接写 `pandas` 而非 `pandas>=1.5`），最大化兼容；后续再做版本锁定 + 冲突检测（见 §6 风险）。

## 5. D5 分析：独立 .py 文件如何配参 + 通用化铁律

### 配参机制
- 每个组件一对文件：`<name>.py`（逻辑）+ `<name>.manifest.json`（`params` 定义）。
- 前端 `ParamForm.vue` 读取 manifest 的 `params` 自动渲染表单（`string/number/boolean/select/textarea/file`）。
- 执行时，编排器把用户填的参数字典作为 `run(params, context)` 的 `params` 传入。

### 通用化硬约束（直接回应"不要硬编码组件"）
1. **所有可变配置必须来自 `params`**，禁止把路径、阈值、关键词等写死在代码常量里。
2. **所有输出产物写到 `context["artifacts_dir"]`**，禁止写死绝对路径。
3. **Secret 一律走 params**（如 API key 作为参数，运行时由用户/系统注入），代码内禁止明文。
4. **组件是纯逻辑**：`run(params, context) -> data`，不依赖全局状态、不在模块顶层执行副作用。
5. 提供 `if __name__ == "__main__":` 自测块，便于脱离系统独立验证。

> 这 5 条写进 Skill 文档的"强制规范"，AI 生成组件时作为约束条件。

## 6. 组件统一契约（最终实现目标）

```python
def run(params: dict, context: dict) -> Any:
    """
    params:   用户配置（键名对应 manifest.params）
    context:  {
        input_data,        # 上一步/输入源数据（已按 input_requirement 解析）
        artifacts_dir,     # 产物目录
        source_type, source_content, source_file_path,
        db,                # 可选
        llm_call(...)      # 可选：经配置端点的 LLM 调用封装
    }
    return: 处理后的数据（作为下一步 input_data）
    """
```

系统组件与个人组件共用**同一契约 + 同一 manifest 结构**，仅 `source` 字段（`system`/`custom`）与存放位置不同，运行时合并进统一 `COMPONENT_REGISTRY`。

## 8. 风险与待确认

1. **依赖版本冲突**：多组件 require 同包不同版本。缓解：第一版不锁版本；后续引入冲突检测 + 提示用户手动 pin。
2. **原生依赖装不上**：如 `playwright` 需浏览器二进制、某些包需 C 编译。缓解：`needs_setup` 状态 + 手动安装提示。
3. **安全边界**：组件在同一进程执行任意 Python，恶意/有 bug 的组件可拖垮 App。缓解：第一版同进程 + 严格 `try/except` + 超时；后续可对 `custom` 组件用子进程隔离。
4. **解析覆盖度**：docx/pdf 解析需新增（python-docx / pdfplumber），列为绿地组件，不在首批内置。
5. **需你最终确认**：D1（解析内置）、D2（`input_requirement` 命名）、D4（全局合并依赖）、阶段顺序是否照此推进。
